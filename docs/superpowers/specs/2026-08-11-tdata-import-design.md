# Безопасный импорт Telegram Desktop `tdata`: исследование и ТЗ

## Цель

Добавить в AI Sales Manager контролируемый импорт **собственного** Telegram Desktop `tdata` как ускоренный способ подключения уже авторизованного аккаунта. Основным способом остаётся вход по номеру телефона; QR — резервный. Импорт `tdata` не заменяет согласие владельца аккаунта и не предназначен для обхода авторизации Telegram.

## Исследование рынка и исходников

| Решение | Результат оценки | Решение для проекта |
|---|---|---|
| [Telegram Desktop](https://github.com/telegramdesktop/tdesktop) | Официальный исходник формата Desktop; формат внутренний и меняется. | Использовать только как техническую спецификацию/референс алгоритмов, не копировать большие фрагменты без проверки лицензии и происхождения. |
| [TDLib](https://github.com/tdlib/td) | Зрелая официальная библиотека для Telegram-клиентов; управляет своим локальным хранилищем, но не даёт публичного импорта Desktop `tdata`. | Возможный будущий runtime-клиент; не решает импорт `tdata`. |
| [Telethon](https://docs.telethon.dev/) | Зрелый Python-клиент, уже используется в прототипе. | Оставить транспортом контролируемой Telegram-сессии. |
| [opentele](https://github.com/thedemons/opentele) | MIT, но PyPI-релиз последнего поколения датирован 2022 годом; проект сам предупреждает о риске блокировок при неверном API-профиле. | Не включать как dependency; допустим только как неисполняемый исторический референс. |

Вывод: готового проверенного production-компонента для этой задачи нет. Нужен собственный минимальный адаптер с чистой реализацией и независимыми тестами; нельзя «вендорить» или исполнять сторонний конвертер с полномочиями действующей сессии.

## Границы и модель угроз

`tdata`, Telethon `.session` и session string — высокочувствительные данные: тот, кто ими владеет, может получить доступ к действующей Telegram-сессии. Двухэтапный пароль Telegram защищает новый вход, но не должен рассматриваться как защита от неограниченного кода, читающего уже авторизованную desktop-сессию.

Разделить два разных секрета:

1. **Telegram 2FA password** — пароль аккаунта, вводится пользователем только локально при необходимости Telegram.
2. **Telegram Desktop local passcode** — пароль, защищающий локальное `tdata`; никогда не логируется, не хранится в БД и не передаётся в браузерный API.

Обязательные ограничения:

- Первый релиз — только локальный одноразовый импортёр на машине владельца. Исходный `tdata` не отправляется в Railway.
- Offline parser не имеет сетевых вызовов. Любой сетевой шаг после него разрешён только к Telegram через текущий контролируемый connector.
- Не использовать spoofing устройства, чужие API ID/API hash или механику, предназначенную для обхода ограничений Telegram.
- Читать только копию `tdata`, созданную при полностью закрытом Telegram Desktop; запретить symlink/reparse points, проверить владельца, размер, hash и неизменность файла.
- Не сохранять raw `tdata`, auth key, passcode, номер телефона или session string в логах, Git, test fixtures или аналитике.
- Временные данные удалить в `finally`; в БД допускается только новая сессия, зашифрованная существующим `SESSION_ENCRYPTION_KEY` с версией ключа.
- Railway не получает raw `tdata` до появления отдельного изолированного worker-а с allow-list egress и независимого security review.

## Целевая архитектура

```text
Пользовательская копия tdata
  → local preflight (путь, no-follow, hash, passcode)
  → offline parser (без сети)
  → explicit consent + controlled Telegram verification
  → encrypted SessionMaterial
  → существующий SessionRepository / quarantine
  → Telegram connection supervisor
```

`local preflight` и `offline parser` не знают о БД и Telegram API. Контролируемый verification слой принимает только валидированный материал, выдаёт пользователю masked account identity и требует явного подтверждения до сохранения. При ошибке материал уничтожается.

## Нефункциональные требования и критерии приёмки

- Поддержать сначала один зафиксированный образец: Telegram Desktop Portable Windows 7.0.9, один тестовый аккаунт B. Новые версии — только после добавления fixture и regression test.
- Не использовать реальный `tdata` в тестах; fixtures должны быть синтетическими, с недействительными ключами.
- Успех: импортёр корректно отклоняет все небезопасные входы; на добровольном тесте B создаёт контролируемую сессию, подтверждает владельца, переживает restart и удаляет временную копию.
- Неуспех/изменение формата: fail closed, без частично сохранённой сессии и без сетевых fallback-запросов.
- До production: независимый code review, проверка лицензий, egress policy для worker-а, ручной тест отзыва сессии в Telegram Devices.

## Не входит в эту задачу

- Массовый импорт множества аккаунтов.
- Загрузка `tdata` через веб-интерфейс или Railway.
- Обход кодов, 2FA, ограничений или политики Telegram.
- Имитация «официального» клиента, случайные device fingerprints и антидетект.
